[1] (P) A lot is being written about AI security these days, and it is not an exaggeration to say that just about everybody has something to say in this fast-changing and evolving space. As if on cue, shortly after I started writing this post, Microsoft’s Satya Nadella weighed in saying that LLMs shouldn’t be trusted, and this from a CEO whose company sells both AI services and compute to train AI models. Strange times. I think it would be helpful to zoom out for a broader and more longitudinal perspective on AI agents and AI solution architecture through the lens of normalization of deviance. That concept came to the forefront during the NASA Challenger explosion investigation in the 1980s, describing an unsafe condition being considered normal provided it didn’t immediately lead to a catastrophe.
[2] (P) Until it did.
[3] (P) A Review of Solution Architecture Diagrams
[4] (P) Let’s go way back to the late 1990s. The following image is a re-creation of the “EJB Components Implement Business Logic” figure from the Simplified Guide to J2EE by Sun Microsystems (1999). Java had been out for a few years at that point, and conceptions of “enterprise Java” started forming for building standardized web-applications and modules of re-usable business logic. Just create a Java Server Page (JSP) and connect it to an Enterprise Java Bean (EJB) that is connected to a data source, and presto!
[5] (P) To be fair, the diagram was meant as an overview and to represent major concepts. I started developing in Java in 1996 and had already produced several solutions during this timeframe, but I already knew the reality was a lot more challenging that those high-level boxes let on. The goals were reasonable though while Java had made big inroads on the server-side programming, application server web frameworks were proprietary. The JSP specification was released in 1999, and in the ensuing years developers ended up requiring a long list of supplementary and sometimes competing frameworks to make them work (e.g., Struts, Java Server Faces, Struts2, etc.), but it could work. EJBs turned out to be a story of their own that left just about everybody unhappy, but the general idea of layered functionality was a foundational principle of software engineering. Java could be deployed quite effectively in many solutions, but the devil was in the details. While web application security is neither simple nor easy, there was some comfort in knowing that in general the bad actors were on the left side of the diagram. The primary threat was on the outside. Ah, the good old days.

[14] (L) Content filters. This filter helps you detect and filter harmful text or image content in input prompts or model responses. Filtering is done based on detection of certain predefined harmful content categories: Hate, Insults, Sexual, Violence, Misconduct and Prompt Attack. You can configure the filter strength for each of these categories based on your use cases. These categories are supported for both Classic and Standard tiers. With Standard tier, detection of undesirable content is extended to protection against harmful content introduced within code elements including comments, variable and function names, and string literals.
[15] (L) Denied topics. You can define a set of topics that are undesirable in the context of your application. The filter will help block them if detected in user queries or model responses. With Standard tier, detection of undesirable content is extended to protection against harmful content introduced within code elements including comments, variables and function names, and string literals.
[16] (L) Word filters. You can define a set of custom words or phrases that you want to block in the interaction between end users and generative AI applications. Custom word filters use case-insensitive whole-word and whole-phrase matching. For example, you can block profanity (use a ready-to-use option) as well as custom words such as competitor names.
[17] (L) Sensitive information filters. You can configure this filter to help block or mask sensitive information, such as personally identifiable information (PII), in user inputs and model responses. Blocking or masking is done based on probabilistic detection of sensitive information in entities such as SSN, Date of Birth, Address, etc. This filter also allows configuring regular expression based detection of patterns (custom regex).
[18] (L) Contextual grounding checks. This filter helps you detect hallucinations in model responses if they are not grounded (factually inaccurate or add new information) in the source or are irrelevant to to the user’s query. For example, you can block or flag responses in retrieval-augmented generation (RAG) applications. If the model responses deviate from the information in the retrieved source or doesn’t answer the question from the user. With Standard tier, contextual grounding checks support responses that include reasoning or conversational content, return more consistent scores, and support additional languages.
[19] (L) Automated Reasoning checks. This filter helps you validate the accuracy of foundation model responses against a set of logical rules. You can use Automated Reasoning checks to detect hallucinations, suggest corrections, and highlight unstated assumptions in model responses.

[21] (P) There are impressive amounts of engineering being spent dedicated to preventing AI agents from making mistakes, getting mis-used, or going rogue. On one hand it is good to see AI safety complexities being recognized, but I think it is easy to take for granted how much of this configuration is about trying to protect the enterprise from its own solution. It is hard enough keeping the bad guys out, but can our own agents be trusted to stay in their cages? This is the new AI design problem.
[22] (P) Dangerous Pets
[23] (P) Hunter S. Thompson once described treating someone as a “pet cobra”: impressive looking, kind of cool to have around, but someone to never turn your back on. I think this an apt moniker for AI agents currently, especially given Satya Nadella’s recent statement: “Business should treat LLMs as potential ‘insider risks’ and set up an ‘emergency brake’ system to keep them in line.” Nobody ever talked about putting emergency brakes on components like databases, middleware, or application servers. A revolutionary game-changing technology that happens to be an insider risk and also needs an AZ-5 button—this is the new AI normal.
[24] (P) When considering the need for agentic activity, it is worth always keeping in mind what the original problem is and look at all of the ways a particular problem could be addressed. Agents might be powerful and perhaps just the ticket, but don’t lose sight of the fact that the fancy new thing in the center of the architecture diagram might be trying to size you up and escape.
